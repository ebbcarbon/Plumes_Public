# case46 — `nearfield_flags[1]` is the stop-at-surface checkbox (2026-08-24/25)

The controlled pair that decodes one `.prj` field: **one geometry, one exe session, one checkbox
moved.** It closes PLAN §8e debt 3, and it retires the standing suspicion that the exe rewrites
that flag behind the operator's back — it does not; **our own experiment note was telling the
operator to move it.**

Generated by `studies/pending_experiments.py`; the experiment note carrying the predictions, all
registered before either run, is kept as [`EXPERIMENT_NOTE.md`](EXPERIMENT_NOTE.md).

## The pair

case13's geometry — the upstream example: 18 ports, 6.1 m spacing, 0.076 m ports at 11 m depth,
0 psu effluent at 0.3505 m³/s into a 32 psu ambient, 30° discharge into a 0° current, output
interval 1.

| | box **ticked** | box **unticked** |
|---|---|---|
| trace | `surface_ON_legacy.dat` | `surface_OFF_legacy.dat` |
| as-run project | `surface_ON_legacy.prj` | `surface_OFF_legacy.prj` |
| **`nearfield_flags[1]`** | **1** | **0** |
| last step | 275 | **476** |
| terminating event | `Plume surfaces` | `Plume traps` |
| final dilution | 169.754 | **217.021** |

⭐⭐⭐ **Every other flag is identical between the two**, and the first **275 steps are
bit-identical — worst difference 0.0 over 13 columns.** So the box changes where a run *stops*,
not what it computes, and `flags[1]` is that box with **1 = stop**.

All four predictions registered before run B hold, two of them exactly: the step count was
predicted as *"roughly 476"* and came back 476.

## ⭐ What it retracts

Ledger row 187 recorded that *"every generated run comes back with `nearfield_flags[1]` flipped
from 1 to 0 by the exe"*. It was never the exe. `plumes2.experiments`' default settings tuple had
said *"stop plume at surface hit: unticked"* on every generated experiment for weeks, so the
operator was — correctly, on our instruction — unticking it every time. The instruction was
removed from the default on 2026-08-24, and this pair is the confirmation that removing it was
right.

⚠️ It also means the counter-evidence was a **stale file**: case13 and case14 have byte-identical
projects that stop differently, which looked like proof the file carries nothing. Since the exe
writes the `.prj` on every run, that cannot be what it looked like — case14's archived project is
the *generated* one copied into both directories, not its as-run state. The test19 / test34-35
failure mode, a third time.

## ⚠️ Two builds in this folder, and the filenames carry it

`surface_ON_current.dat` is the **current build**; the pair is the **old** one. Same project, same
box (ticked), near field **bit-identical over all 275 steps × 13 columns** — and a wastefield width
of **96.29 m** against the pair's 109.59 m, which is `cos 30°` exactly. That is row 275's build
split reproduced deliberately on one geometry, and it is why this folder cannot be classified by
directory.

| trace | implied span factor | `|cos 30°|` | build |
|---|---|---|---|
| `surface_ON_legacy.dat` | 0.9943 | 0.8660 | **old** (no cosine) |
| `surface_OFF_legacy.dat` | 0.9964 | 0.8660 | **old** (no cosine) |
| `surface_ON_current.dat` | **0.8660** | 0.8660 | **current** (cosine applied) |

⭐ The two old-build traces carry `legacy` in their filenames so `validation._is_old_build`
classifies them by its naming rule rather than by a hand-maintained list. Three separate runs have
previously landed as old-build files inside current-build folders and each time failed ledger
row 96 by ~13.6 m until someone noticed; the naming rule exists so a trace classifies itself.

⚠️ The **111.12 m** width on the unticked run is *not* a third build. That run stops in a different
place, so its near-field endpoint and final plume diameter differ and Brooks starts from a
different width. Both pair members are the no-cosine arm.

## Loose ends

- ✅ **`nearfield_flags[3]` reads 2 in both runs** where the experiment note asked for **3** —
  settled 2026-08-26 from the files: `generated_template.prj` already carried 2 (its base is the
  upstream example) and the exe writes the as-run state, so the setting was left alone. The
  trace agrees: the port's solver on run B with rise/fall **2** ends at 102.0 s against the exe's
  105.9 s (the known late-trajectory drift); with 3 it ends at 131.8 s. `flags[3]` is the count.
- `generated_template.prj` is the file the generator writes, kept so the case can be re-run from
  the same starting state. ⚠️ It is **not** an as-run project: an earlier copy of it was truncated
  by the exe from 154 lines to 109, losing its whole output-selection tail, which is why the
  experiment had to be regenerated before run B could be made at all.
